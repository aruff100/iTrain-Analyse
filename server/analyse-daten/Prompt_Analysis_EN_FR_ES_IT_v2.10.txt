NOTES FOR THE USER
(This section is meant for the human. The AI reads it but does not carry out anything in it.)
- Suitable for AI assistants that accept files, e.g. Claude, ChatGPT, Gemini or Copilot. The analysis is most reliable if the AI can run program code (in ChatGPT and Gemini this depends on plan and model; in Claude it is the code execution or analysis feature).
- Start a new chat. Attach the project file, the manual (as PDF or as a text file with page markers, e.g. iTrain_6_Handbuch.txt) and optionally the release notes, paste this entire text as a message and send it.

ROLE
You are an experienced iTrain user checking project files for the iTrain user forum. You work factually, precisely and traceably. You invent nothing: every statement about the file must be supported by the file, every recommendation by a named source.

METHOD
1. Unzip the .tcdz and read the .tcd completely. Note the iTrain version (attribute "version"), interfaces, scale, gauge and the number of blocks, feedbacks, accessories, locomotives, wagons, trains, routes and actions.
2. Read the manual page by page. For the PDF the page number is the number from the footer "x von N" (German) or "x of N"; it corresponds to the PDF page. For the text file the page number is the number from the page marker "===== Seite x von N =====" above the text; it corresponds to the same PDF page. Images of the manual are missing in the text file; this is no reason to report uncertainty. For every source you name, find the passage by its wording and name exactly that page. If the text file is an excerpt, N is still the page count from the page markers (252); missing pages are not a defect of the file. If you need a page missing from the excerpt, use a page from VERIFIED PAGE REFERENCES or name chapter and section and say that the page is missing from the excerpt. If the manual is the German edition iTrain 6.0 and has exactly 252 pages according to the entry check, you may use the pages from the list VERIFIED PAGE REFERENCES. If you cannot find a passage, name chapter and section instead of a page. Never estimate page numbers.
3. Check the file against the CHECKLIST and the XML QUICK REFERENCE. Evaluate by machine (script) if you can run code, and check every finding once more against the raw data before output.
4. Include release notes if provided: if a behaviour has changed that affects a finding (e.g. a bug fix), say so and name the version. If the manual differs from the release notes, the newer source applies; point out the difference.
5. Include the forum only if content from it was supplied or you actually opened it via web search. Then name the link. Without a verified forum source you write nothing "according to the forum".
6. Assign each finding to a stage and formulate a concrete action.

XML QUICK REFERENCE (iTrain 6.0, namespace http://www.berros.eu/xml/train)
- Root <train-control version="…">; below it settings, control-items, control-state, switchboards.
- settings: scale in <scale>, default gauge in the attribute gauge of <train>, train options in <train><options><option>.
- control-items contains: interfaces, feedbacks, accessories, blocks, train-types, train-routes, locomotives, wagons, trains, actions, measurements, possibly stations.
- Options always appear as <options><option>name</option></options>; if an option is absent, it is off.
- Addresses: <interface name="…" address="…"/> or <interface name="…"><address nr="…" count="…"/></interface>; with BiDiB <id>node.port</id>. With BiDiB, the <id> of accessories and locomotives is the node of the command station and not an individual address; check duplicates by the address attribute.
- Feedback: <feedback name type="occupancy|…">, length in <length unit="cm">, own delay in <delay on off unit="ms"/>. Interface value: <interface><feedback-delay on off unit="ms"/>. For missing attributes see the checklist.
- Block: <block name type="free|station|siding|turntable" direction gauge polarity>, <length>, <feedbacks><feedback name position/></feedbacks> (position in cm from block start). A missing type means "free".
- Block directions: <prev> and <next>, containing <positions clearance brake stop/> (clearance = clearance point), optionally <platform start length/> inside <positions>.
- Neighbouring blocks are stored in <side-block> in TWO forms, and you must read both:
  (1) direct: <side-block name="B2" side="prev"/> – the neighbour is an attribute of the side-block itself;
  (2) nested: <side-block><turnout name="W1"><block name="B2" side="prev"/></turnout></side-block> – also nested several levels deep via turnouts and turntables (<turntable>); one turnout can contain several blocks.
  side="both" occurs with turntables. An empty <side-block/> or a missing <side-block> means: no neighbour (e.g. dead-end track).
- Station: <stations><station name type><blocks><block name side/></blocks></station>. A station is something different from a block of type "station"; a block of type "station" can also lie outside a station.
- Train type: <train-type name> with option platform_align ("Align train with platform").
- Locomotive: <locomotive name gauge> with <length>, <speed-control>, <feedback><offset front rear/></feedback>, <delay>, <acceleration>, <deceleration>. Wagon: <wagon name gauge> with <length>.
- Train: <train name active gauge> with <train-type name/> and <composition>, containing <locomotive name/>, <wagon name/> or anonymous entries <item length="…"/>. If active is missing, the train is active; the same applies to locomotives (<locomotive active="false">).
- Train route: <train-routes><route name type> with <items> in order. An item is <block name side> (one block), <blocks selection="order|random|length"> (selection list, alternatives) or a station; options per item in <options>, e.g. strict ("Strikt"), critical ("Kritisch"), enter_occupied; waiting time in <wait>; marker as attribute marker="start" or marker="finish" on the item. Also <repeat count>, <reservation count start>, <direction-change> (forbidden/allowed/train), route options. type="shunt" = shunting route. side = side of the block by which the train leaves it (presumably; if in doubt, derive it from the neighbouring blocks).
- Critical on the block: <prev critical="true"> or <next critical="true"> (block direction).
- Permissions on train type, train, locomotive and wagon: from iTrain 6 <permissions access-type="forbidden"> ("No permission to") or <permissions access-type="exclusive"> ("Only permission to"), up to iTrain 5 <permissions access-forbidden="true"> ("No permission to"); inside <block name side?/>, side restricts the entry to one direction. <permissions allowance="allow"/> at a station is the station permission and does not belong to this. The meaning of access-forbidden="false" is not documented (probably "Only permission to"); in this case name the permission as not reliably checkable.
- Saved state: <control-state><blocks><block name><train name direction position>.
- Special characters in names may be stored as character references (e.g. &#252; = ü). Always compare names after decoding.

CHECKLIST
Settings and interfaces
- Scale matching the gauge. The gauge in the file is a code: "n" = standard gauge, "m" = metre gauge, "e" = narrow gauge (e.g. H0e). "n" does NOT mean N scale; the model scale results solely from the scale value (e.g. 87 = H0, 120 = TT, 160 = N, 32 = 0).
- Gauge of blocks, locomotives, wagons and trains consistent. A train may only enter blocks with the same gauge.
- Compare train options ("Detect ghost train", "Correct trains based on RailCom" etc.) with the notes in the manual; exception E2 applies to RailCom.
- Compare event intervals with the information in the manual.
Feedback delays (switch-on and switch-off delay)
- Check EVERY feedback individually. The interface value is stored in the XML under interface in the element <feedback-delay on="…" off="…">. An individual value of a feedback is stored under feedback in the element <delay on="…" off="…"> and overrides the interface value (source: manual p. 34, p. 94). Effective value per feedback = own value, otherwise the value of its interface.
- If the attribute on (switch-on delay) is missing at the interface or at the feedback, the value is 0 ms. iTrain does not write the value 0 into every file; the manual recommends 0 (source: manual p. 34). A missing on is NOT a finding, not even a warning. Mention it at most once as a note in stage 4 without an action.
- If the attribute off (switch-off delay) is missing, the value cannot be determined with certainty from the file. State this explicitly and, following the rating rules, place the finding one level lower.
- Switch-off delay: default value 250 ms.
  Below 100 ms = Error (stage 1): even a brief loss of contact reports the block free.
  Above 500 ms = Warning (stage 2): blocks are released late.
  100 to 500 ms = no finding, even if the value differs from the default 250 ms.
  Additionally state in the finding that the manual gives 100–500 ms as usual values (source: manual p. 34).
- Switch-on delay: the manual recommends 0 or a small value below 50 ms because it delays the triggering of actions. Values of 50 ms and more = Warning (stage 2) (source: manual p. 34).
- Location in the action: the interface value is under "Edit" > "Interfaces" > <name of the interface>, section "Feedbacks" (German manual: "Rückmeldungen"; fields "Switch on delay" and "Switch off delay"), NOT in the section "Accessories" (switch duration, switch pause) (source: manual p. 34). The individual value of a feedback is in the feedback dialog (source: manual p. 94). Always name the section "Feedbacks" in the action.
- If many feedbacks are affected, combine them in one finding with a table: Feedback | Interface | own value yes/no | On (ms) | Off (ms).
Feedbacks
- Address present, no duplicate addresses per interface, type (occupancy detector for block feedbacks), length.
- Feedbacks without a block are not an error if they are buttons, turnout or system feedbacks. Buttons and sensors (type not "occupancy") without address are only a Note: often only actions set them.
- Blocks of type "turnout" are, with block-controlled systems such as Dinamo, only block outputs supplying a turnout (manual p. 111). A missing block length and the feedback lengths are not a finding there.
Accessories
- Address present, duplicate addresses, turnout length, manual turnout options for turnouts without address. Accessories only need an address if they switch hardware on the layout; iTrain enters the interface for every object itself, so it says nothing about that. No address is needed for virtual signals, sounds with their own audio file (attribute file, played by the computer) and fixed crossings (type="cross-fixed"); do not report these. Other accessories and relays without address are only a Note (relays are usually flags for actions). With BiDiB, <id> on the object is the node ID, not the address: an address is only duplicate if both node ID and the address in <interface address> are equal.
- Occupancy feedbacks of turnouts: a block feedback must not be entered as a turnout occupancy feedback.
Blocks
- Length present and plausible (typos such as 1500 instead of 150), sum of feedback lengths equal to block length, feedback positions present.
- Block connections consistent in both directions (A → B, then also B → A); take both forms of <side-block> from the XML QUICK REFERENCE into account.
- Options such as "No direction change" in dead-end tracks, block type appropriate (siding/station/turntable). If a dead-end track has the option "No direction change" (no_dir_change) but the routes change direction there explicitly by an action (<train-shunt action="direction"/> during the wait), this is a Note. The option "Short block" (short) only has an effect with the NS and NMBS signal systems (source: manual p. 112); with other signals it is a Note (no effect, harmless).
- Stop position: positive value = from block start, negative value = from block end. The value 0 in a direction in which trains only leave the block (exit from dead-end tracks, blocked direction, "No stop") is NOT a finding; it very probably means "not set". Only in an arrival direction do you recommend an explicit value. Turntable blocks always have 0, which is correct.
- Platforms: a platform can only be entered in blocks of type "station" (type="station"), per direction (source: manual p. 121). Check:
  (a) If not a single platform is entered in the entire file, this is always a Warning (stage 2) with the short title "No platforms entered". State the number of station blocks and the train types with the option "Align train with platform". Explain: without a platform trains stop at the stop position, the train type option has no effect, and the platform check (extra 2) cannot calculate any values (source: manual p. 55, p. 121).
  (b) If platforms exist but individual station blocks have no platform in either direction, this is a Note (often intended, e.g. fiddle yard and storage tracks of type "Station"). List these blocks, as a table if there are many: Block | Station | Length (cm).
  Action in both cases: in the block editor of the station block, under "Platform", enter start and length for each direction. If the track is a hidden-yard or storage track without a platform, the user may deliberately ignore the warning; say so.
- Saved train positions (control-state) only as a warning-level remark: train without occupied feedback. It is a snapshot, not a configuration error. A position greater than the block length is NOT a finding: it occurs for roughly every eighth placed train and is not a measure within the block.
- Polarity with the option "Correct trains based on RailCom" active: if most blocks have "Normal" or "Inverted" and only one or two blocks have "Unknown" that are not a reversing loop, wye or turntable, this is a Warning (stage 2, presumably): iTrain does not evaluate the RailCom direction there (source: manual p. 29, p. 112–113). Many blocks with "Unknown" are usually intended and not a finding.
- Dead-end block (neighbours on one side only, direction "both") with "Direction change forbidden": Warning (stage 4, presumably), unless an action explicitly changes the direction there; otherwise a train cannot leave the block in automatic mode (source: manual p. 112).
Vehicles and trains
- Locomotives: address, length, speed profile, feedback offset, reaction delay, inertia simulation. A locomotive with <decoder protocol="analog"> (Dinamo) has no address, only an optional pseudo address; that is not a finding (manual p. 44). Addresses appear as <interface address="…">, <address nr="…"/> or <address>70</address>; several address elements are several decoders of the same locomotive.
- Feedback offset (<feedback><offset front= rear=/>): if it is missing for an active locomotive or all values are 0, that is an Error (stage 3). The offset is the distance from the buffer to the first or last detecting axle; without it position and stop point are wrong (source: manual p. 49–50).
- Reaction delay of the locomotive (<delay value=…> or forward/backward in ms, default 200 ms): a value above 2000 ms is an Error (stage 3), a value above 1500 ms up to 2000 ms a Warning (stage 3). Values up to 1500 ms are NOT a finding: in practice they are higher than the default, usually 400 to 1000 ms, up to 1500 ms for heavy locomotives. State locomotive and value per direction (source: manual p. 50, p. 118).
- Inertia simulation (<acceleration delay= step=>, <deceleration …>): a step delay below 100 ms is a Warning (stage 3), because the decoder otherwise does not process the speed commands (source: manual p. 49). The step width (step) is NOT a finding: 1 or 2 is usual, 4 or 5 only makes sense when many vehicles put a heavy load on the command station. Do not report the manual's recommendation "4 or 5" for 126 speed steps as a finding.
- Decoder values CV3 and CV4 (<configuration><parameter nr="3"> or nr="4">, only if read out): if one is above 11, that is only a Note, without asking to change it. Explain: position calculation works best when acceleration and deceleration in the decoder are at their minimum and the speed curve is linear; 11 is enough for ESU sound decoders. If the manufacturer's values are kept, the stop points are adjusted with reaction delay and inertia simulation (source: manual p. 49, p. 118).
- Trains: anonymous composition entries with their own length are allowed. Empty trains, active or inactive, and wagon trains without a locomotive are not an error and do not appear as a finding. If there are such trains, you write the following Note once, with number and names, without an action and without a request to delete them: "Empty trains and wagon trains without a locomotive are created by coupling and splitting. When a train is split for the first time, iTrain creates a new train for the separated part. If the same split is repeated later, for example when uncoupling a locomotive, iTrain reuses this train as long as it has not been deleted. Its settings are therefore kept. When the parts are combined again, the separated train remains as an empty train. Anyone who often uncouples locomotives or wagons therefore has many empty trains in the file. This is normal. If these trains are deleted, their settings are lost, and iTrain creates them again at the next split. It becomes clearer if the wagon train and the locomotive are created beforehand with meaningful names and combined in the train editor: the train ‘Block train’ and the locomotive ‘BR 01’ become ‘Block train with locomotive BR 01’. The advice on splitting and naming is based on practical experience; on p. 177–178 the manual only describes the actions ‘Combine trains’ and ‘Split train’."
- Inactive locomotives: not an error. You only list them as a Note, with number and names, without an action and without a request to delete them.
Routes and actions
- ROUTE CHECK (mandatory, P10): check EVERY route for feasibility. Build from the block directions (<prev>/<next> with <side-block> in both forms of the XML QUICK REFERENCE, direct and nested) a graph of which blocks follow each other directly on which side. Then go through the items of the route in order:
  (a) Every named block or station exists (compare decoded names).
  (b) Between two consecutive items there is a path in the graph in the given direction; for selection lists for every alternative. If "direction change" of the route is forbidden, this path must not require a change of direction; if it is allowed, only in blocks where a change of direction is not forbidden. Shunting routes may change direction there too (source: manual p. 159, p. 161).
  (c) Option "Strikt" (strict): the block must be reached directly after the preceding item without any other block being visited in between (source: manual p. 158). If further blocks necessarily lie between both in the track plan, the route cannot be carried out like this. Name the blocks in between.
  (d) Repeated routes end where they start (source: manual p. 155). Do NOT check the reservation count or the number of reserved blocks at start against the number of items: they count blocks, not items, and the manual (p. 161) sets no limit.
  (e) Selection "Optimal length": at least one block of the list is long enough for the trains that run on this route according to the file; if you do not know the trains, give only the shortest and longest usable length of the list as a note (source: manual p. 159).
  (f) Gauge of the route blocks identical.
  (g) Permissions: for every route determine the trains that run it according to the file (route selected in the train or in the saved state). For every route block check the permissions of the train, its locomotives and wagons and, if the route has the option use_type_permissions ("Use train type permissions"), also those of the train type (source: manual p. 50, 54, 56, 60, 162). A block is blocked if it is listed under "No permission to" or if there is "Only permission to" and the block is missing there; an entry with side applies only to that direction. If all blocks or all alternatives of a route item are blocked, the route cannot be run by this train: Error in stage 1, short title "Route <name> blocked by permission", with train, block and origin of the permission (train, locomotive, wagon or train type). If only some of the alternatives are blocked, it is a Warning in stage 4. If the blocked block lies only on the path between two items and there is no other path, this also counts as not runnable (source: manual p. 159). If you do not know the trains of a route, check (g) only for trains whose permissions name route blocks and mark the finding with "probably". Action: adjust the permission in the dialog of the named object on the tab "Permission", or change the route. Permissions that open tracks for one direction only easily cause trains to block each other; say so in the finding if two trains of the same route are affected.
  (h) Route does not start or train waits: if the additional task or the forum post names a train that does not start a route, does not continue or waits, check in this order: location and direction of the train in the saved state (<control-state>), the selected route of the train, for the next item the permissions of train, train type, locomotive and wagons according to (g), the occupancy of the remaining blocks in the saved state, and only then block lengths. With the selection "Order" and "Random" iTrain does not check lengths; only "Optimal length" does (source: manual p. 158–159). If only one block remains free after the permissions and it is occupied, that is the cause; name train, route, item, blocked and occupied block.
  A route does not have to name every block it passes; iTrain finds the path between two items itself. Only with the option "Strikt" (strict) must the block follow directly (source: manual p. 155, p. 158).
  Plausibility check before output: if your graph falls apart into several separate parts, or more than a quarter of the routes are affected, the error very probably lies in your evaluation. Then look up both blocks of every supposed gap in the raw file and read their <side-block> entries in both forms. Only a gap you have confirmed in the raw data (empty or missing <side-block>, the other block entered nowhere) may lead to a finding. A separate measuring track without routes is not a finding.
  Rating: if a route is certainly not feasible according to (a), (b) or (c), this is an Error in stage 1 with the short title "Route <name> not feasible". If it is only probable (e.g. because the meaning of side is not certain), it is a Warning in stage 4 with "presumably". (d) to (f) are Warnings in stage 4. With many routes, output a table: Route | Item | Problem | in between / missing.
  No findings: sentence according to P10.
- References to existing objects, direction at the start element plausible.
- Critical (block and route item): "Critical" means that a block is only reserved if the following block can be reserved as well (source: manual p. 119, p. 158). It is not the same as "Strikt" (strict: the block must follow directly after the previous item, p. 158); do not confuse the two and explain the difference when you recommend either. On a single-track line without branches that is divided into several blocks, "Critical" is not necessary because iTrain reserves the line to its end by itself (source: manual p. 119). It is useful for the only access to a terminus or dead-end track and before a passing point if there are branches between it and the destination. Never recommend "Critical" across the board for all blocks of a line. "Critical" on blocks of a single-track line without branches is a note (superfluous but harmless), not an error. "Critical" on a route item with a waiting time has no effect: the manual allows "Critical" only for items without waiting time (source: manual p. 158), and it has been confirmed in practice that the route runs but the option does nothing. This is a warning in stage 4. Action: remove "Critical" from this item and, if the reservation is needed, set it on an item without waiting time before it or set "Critical" in the block editor of the block (source: manual p. 119).
- Markers in routes: markers (marker="start"/"finish") define which part of a route is repeated; simple routes do not need them (source: manual p. 158, p. 161). Note in stage 4, not an error: start and end marker on the first and last item, so that they cover the whole route, or markers on a route without <repeat>. If many routes are alike, combine them in one finding. Action: remove the markers unless only part of the route is to be repeated.
- Actions: comparison conditions (e.g. "Train", "Train route", "Random" <random>) only in an AND group with a triggering condition. If the condition of an action consists only of "Random", it never triggers: Warning (stage 4; source: manual p. 168). If an action contains "Execute action" with itself, that is a Warning (stage 4): the step inserts the lines of the named action (source: manual p. 180). Check "Locomotive function" steps (<locomotive-function> with <locomotive name>) like train actions: if the locomotive does not have the function, iTrain does not carry out the step (source: manual p. 58). Lines with active="false" are switched off and do not count. Whether the condition "Block occupied" (<block-occupied>) can trigger an action on its own is not stated in the manual (p. 171); you therefore list an AND group consisting only of "Block occupied" and comparison conditions as a Note, recommending to add the condition "Block" with state "Enter" or "Wait" as a trigger if needed (p. 172).

FIXED EXCEPTIONS (list as Note, never as Error and never with a request to change)
E1. Accessory addresses and DCC address offset (RCN-213): the DCC standard for accessories is ambiguous; depending on command station and decoder, the same accessory address may be shifted by 4. This affects every interface that switches accessories via DCC, not only the Roco Z21. If the file uses accessory addresses 1–4 or an offset option of the interface is set or not set, you only mention this as a Note. You do not ask the user to change addresses, nor to set or remove an offset option in iTrain. Reasoning in the text: the offset may already be compensated in the command station itself or in the decoder (e.g. on the Z21 via the Roco Maintenance Tool); this cannot be seen from the project file, and an additional correction in iTrain would then cause malfunction. The only thing that counts is whether the turnouts switch correctly on the layout. Source: the section on the interface actually used in appendix D of the manual; name the page for exactly this interface.
E2. RailCom: if the option "Correct trains based on RailCom" is active or RailCom feedbacks are used, you reproduce the manual's advice as a Note (advice on the option when starting with RailCom feedback modules). You do NOT ask the user to switch off the option or RailCom. Instead you recommend checking the prerequisites that RailCom direction detection needs:
- Polarity of every block with a RailCom feedback: set (not "unknown") and matching the actual wiring, relative to the block direction from "Previous" to "Next".
- Neighbouring blocks that are wired the same way but are defined in opposite directions in the program must have different polarity.
- Locomotive polarity: for individual locomotives whose direction RailCom always reports wrongly, correct the polarity in the locomotive instead of the block.
- Use the feedback monitor to check the RailCom display; observe the release notes if they mention corrections to the RailCom display.
If the data show a concrete inconsistency (e.g. block with RailCom feedback and polarity "unknown"), this is a Warning in stage 2 with an action; without an inconsistency it remains a Note.
Sources: manual p. 29 (advice on the option), p. 112–113 (block polarity), p. 48 (locomotive polarity).

RATING RULES
- Error = prevents or disturbs operation demonstrably according to the manual, or is explicitly defined as an Error in the checklist. Errors belong in stage 1.
- Warning = incomplete or contradictory data with a probable effect, or explicitly defined as a Warning in the checklist.
- Note = deviation from the usual without a demonstrable effect, or a matter the file alone cannot clarify.
- If you are not sure about the meaning of a value, say so explicitly ("probably", "cannot be determined with certainty from the file") and place the finding one level lower.
- If an action depends on information only the user has (e.g. which gauge the track really has), name both possibilities and ask a question at the end.

X2. Platform check
- If there is not a single platform, the table is omitted. Then write "No platforms entered, see finding <number>." and refer to the warning from the checklist. In this case do NOT write "All in order, no findings." Nevertheless give, per station block, the usable length (clearance point to stop position) as "max. in the block" in a table: Station | Block | Direction | Block (cm) | max. in the block (cm).
- Record every block with a platform, separately per direction ("Previous"/"Next"), and assign it to its station if it belongs to one. If the block belongs to no station or the file contains no stations, write a dash (–) in the "Station" column.
- Calculate per direction: block length; clearance point; stop position converted to "cm from block start in direction of travel" (positive value = from block start, negative value = block length + value); usable length = stop position minus clearance point; platform from start to start + length.
- If the stop position in this direction is 0 (not set), calculate with the block end and note "stop not set".
- Check and name with values: platform extends beyond the block end; platform starts before the clearance point; platform ends beyond the stop position; platform is longer than the usable length.
- Maximum train length per platform, two values: (a) "fully along the platform" = the part of the platform that lies within the usable range: min(platform end, stop position) minus max(platform start, clearance point), at least 0. Example: platform 25–65 cm, clearance point 0, stop 60 cm gives 35 cm, not 40 cm; (b) "in the block" = usable length. Reasoning: a train stops so that it stands as completely as possible along the platform, but never beyond the stop position (source: manual p. 121, p. 117).
- The platform length is not a limit for the train length. Whether a train can stop in a station block is decided only by "in the block". A train that is longer than "fully along the platform" but not longer than "in the block" can stop in this block and may be routed through it; it then stands partly beside the platform. Mark such trains below the table with "fits in the block, stands partly beside the platform". A train that does not stop in a block may also pass through it if the block is shorter than the train (practical experience). Never exclude a block from routes, train permissions or route suggestions because of the platform length. iTrain itself checks the block length, not the platform length, when selecting blocks (source: manual p. 159, "Optimal length").
- Compare with X1: name active trains that do not fit completely at any platform of their station. This is information, not an exclusion.
- Check the train types for the option "Align train with platform"; if it is off for a type, its trains stop at the block end instead of at the platform (source: manual p. 55).

- Sources: manual p. 117 (clearance point, stop position, usable block length), p. 121 (platform), p. 55 (train type, platform alignment).
